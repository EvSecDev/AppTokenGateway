# App Token Gateway

A simple HTTP server that bridges OIDC user authentication to static per-user API tokens.

## Overview

This is meant for situations where the backend application does not recognize any form of authentication and clients cannot participate in a single sign-on flow.

This serves as both the API token creation/registration as well as seamless token verification through the primary web server.

Registration flow is meant for an interactive user through their browser to create an API token and register it with the server.
In order to tie these tokens to identities, an OIDC provider is required to authorize the user prior to a token being issued.

Once the user sets up their token, that token is used to access the normal application behind the web server without the need for an interactive authorization flow.

Note: This program only supports OIDC providers that use RSA or ECDSA signing keys.

## Installation

Place the executable file in `/usr/local/bin/atg`.

Generate a template configuration file: `/usr/local/bin/atg --template-config`

Edit `/etc/app-token-gateway.json` with your required configuration options (Expected token auth headers, listen address/port, ect.)

Create a systemd service at `/etc/systemd/system/atg.service` using the example service below.

Start the systemd service: `systemctl start atg.service`

Ensure server starts at boot: `systemctl enable atg.service`

## API Tokens

Tokens are generated by the client javascript and sent to this program for storage (after user is authorized).

Tokens themselves are hexadecimal, 32 to 128 characters in length.

Token names are ASCII only, 1 to 64 characters in length.

If a user generates a new token with the same name as an existing and registers it, this overwrites the existing token (effectively revoking the old token).

Any tokens with an expiration are evaluated at use time (not polled and revoked in the background).
If something tries to use an expired token, the request is denied and the token is removed from storage at that time.

Maximum time-in-the-future for expiration dates is 3 months.

All tokens are stored in a separate JSON file by username (email).

Tokens are hashed before storage and comparison.

When a user registers a token, it is immediately written to the local token store file.

## Integration

Example NGINX configuration (HTTP-only example):

```text
server {
    listen 80;
    server_name myapp.example.com;

    location /myapp {
        auth_request /auth;
        proxy_pass http://app-backend.example.com;
    }

    location ~ ^/(register|tokens|revoke|login|callback|auth)$ {
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_pass http://localhost:8080;
    }
    location /atgui {
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_pass http://localhost:8080/atgui;
    }
}
```

---

Example Systemd Service:

```text
[Unit]
Description=API Token Gateway for <App Name>
Documentation=https://github.com/EvSecDev/AppTokenGateway
After=networking.service

[Service]
User=www-data
Group=www-data
StandardOutput=journal
StandardError=journal
ExecStart=/usr/local/bin/atg --config /etc/app-token-gateway.json --start-server
Type=exec
RestartSec=60
Restart=on-abnormal

[Install]
WantedBy=multi-user.target
```
